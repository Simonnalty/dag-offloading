# 答辩预期提问与标准回答（排练用）

> 按"提问 → 回答要点"组织。回答时先给结论再给证据，每题控制在 30~60 秒。

## 建模与仿真器

**Q1：你们的仿真器怎么保证算得对？**
A：三层保障。第一，时序模型逐条对应论文公式（执行时间 w/f、传输 data/B、开始时刻取前驱完成+传输与层空闲的较大者）；第二，我们写了 6 个可纸上手算的小算例，每个算例先手算出 makespan 和能耗，再与仿真器输出逐一核对，全部通过（verify_handcheck.py，可现场跑）；第三，DQN 的训练环境与仿真器是同一套时序的两份实现，二者终局指标在 30 个随机实例上完全相等，交叉验证了实现。

**Q2：参数（算力、带宽、功率）是哪来的？**
A：取自文献中的典型量级：端对应手机级 1GHz、边对应边缘服务器、云对应数据中心；带宽 20~100 Mbps 对应常见无线接入。报告参数表注明了这是"典型量级标定"而非某具体设备的实测。更重要的是我们做了标定敏感性分析：计算量参数若取太小（50~500 MI），传输开销永远占优，最优解退化为全放边缘，测不出算法差异；取 200~2000 MI 后才进入"计算-传输权衡"的有意义区间。

**Q3：为什么每层只有一个执行单元？**
A：这是有意的简化——课题核心是卸载决策算法而非排队系统，单队列已能表现"同层任务相互拥挤"这一关键效应。扩展到多实例排队列在改进方向（离散事件仿真、M/M/c 队列），不影响算法对比的定性结论。

## 算法设计

**Q4：HEFT 和你们的 E-HEFT 到底什么关系？**
A：E-HEFT 保持 HEFT 的 rank 优先级排序不变，只把选层准则从"最早完成时间"改为"归一化时间-能耗加权和"。它有一个可证明的性质：α=1 时与标准 HEFT 的决策完全相同（我们用 5 个随机实例断言验证过）。所以 E-HEFT 可以看作 HEFT 在能耗维度的严格推广，α=0~1 扫描生成时间-能耗 Pareto 前沿。

**Q5：能耗模型的三项是怎么来的？**
A：终端能耗 = 执行电耗 + 等待电耗 + 传输电耗。执行时按执行功率计，空闲期按空闲功率计（端设备不会关机），收发数据按 WiFi 典型发射功率。这个结构是移动边缘计算文献的标准做法；具体数值是典型量级。

**Q6：DQN 的状态为什么这么设计？**
A：13 维全部归一化：当前任务的计算量、是否入口/出口、调度进度（任务自身特征），加上三层各自的就绪时刻、队列空闲时刻、前驱分布（环境特征）。设计原则是"决策需要的因果量都要在"——就绪时刻和队列占用直接决定开始时间，前驱分布决定传输代价，同时控制维度避免维数灾难。

**Q7：为什么 DQN 在 n=100 上退化严重？**
A：训练分布是 n≈10~14 的小图，n=100 超出 7 倍。我们用的是扁平 MLP，它对"图规模"没有结构化泛化能力——节点数变了，状态向量的语义分布就漂移了。这是我们如实报告的局限；文献中的标准解法是 GNN 策略网络（消息传递天然随图大小泛化），已列入改进方向。n=30（2.5 倍）时 DQN 加权目标仍最优，说明适度泛化是成立的。

## 实验与结论

**Q8：为什么不用 GPU 训练？**
A：策略网络只有约 5600 参数，单次前向在 CPU 上微秒级；GPU 调用的固定开销（内核启动、数据搬运）反而更大。实测瓶颈在 Python 环境推进而非网络计算。若升级到 GNN 或大规模超参搜索，GPU 才有意义。

**Q9：DQN 的结果稳定吗？**
A：不稳定——三个训练种子在相同评估集上的加权目标分别是 13.5 / 9.3 / 8.4，方差很大。我们因此做了多种子选优（保留最优权重），这也是 RL 实验方法论的一部分：论文级结论应报告多种子的均值和分布，我们如实报告了。

**Q10：带宽减半时全放云端反而超过 HEFT，怎么解释？**
A：低带宽下终端上传成为全局瓶颈（所有入口数据的必经之路），HEFT 混合放置反而把更多数据流引向了慢速的端-云/端-边链路；全云端虽然算力浪费但数据只需上传一次。这说明**在传输受限场景，经典时延优化算法可能被朴素方案反超**——正是本课题认为需要可学习策略（RL 能从整体目标出发权衡）的动机之一。

**Q11：你们的贡献点是什么？（必问）**
A：三点。① 端到端的可复现实验系统：建模-仿真-5 算法-批量实验-出图全链路，一条命令复现全部数据；② 自设计算法 E-HEFT，在 HEFT 框架上引入能耗维度并证明 α=1 时严格退化为 HEFT；③ 对 RL 在本问题上的系统实验分析：环境一致性验证、训练敏感性、多种子方差、泛化边界——这些负结果/边界结果与正结果同样有信息量。
